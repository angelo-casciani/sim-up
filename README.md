# Sim-Up

An agentic iterative pipeline based on local, open-weight Large Language Models (LLMs) served by [Ollama](https://ollama.com) for process-improvement generation and validation, combining SIMOD and PM4Py baseline simulation models extraction, and a two-fold simulation for the improvement hypothesis validation, supporting control-flow-first simulation via Prosimos and resource-first simulation via AgentSimulator.

## Quick Start

### Prerequisites

- Python 3.11+
- Poetry
- Docker
- [Ollama](https://ollama.com/download) running locally (or reachable through `OLLAMA_HOST`) with at least one [supported model](#llm-setup-ollama) pulled

### Install & Run

Clone the repository locally:
```bash
https://github.com/angelo-casciani/sim-up
```

The event logs in `logs/` are stored gzipped. Extract them in place before running the pipeline:
```bash
gunzip -k logs/*.gz
```
This keeps the `.gz` archives and writes the uncompressed logs (e.g. `logs/p2p.csv`) next to them; the extracted files are git-ignored.

Run the automated setup script (it also reports which supported Ollama models are missing):
```bash
./setup.sh
poetry run python src/main.py --log p2p.csv --model qwen3.8:latest --max_iterations 3
```

<details>
<summary>CLI Options</summary>

| Option | Description |
|--------|-------------|
| `--log` | Input event log (CSV/XES) |
| `--model` | Ollama model tag (default: `qwen3.8:latest`) |
| `--temperature` | LLM temperature (default: 0.0) |
| `--max_tokens` | Max output tokens per LLM call, reasoning included when `--think` is on (default: 4096; the report always gets at least 8192) |
| `--num_ctx` | Ollama context window in tokens, capped at the model maximum (default: 32768) |
| `--think` | Enable reasoning for models that support it (default: off) |
| `--max_iterations` | Number of improvement iterations |
| `--no_sudo` | Run Docker without sudo (needed for Windows) |
| `--des_runs` | Control-flow-first simulation runs (default: 10) |
| `--abs_runs` | Resource-first simulation runs (default: 10) |

</details>

## Web GUI

A Gradio-based web interface is available for interactive use:

```bash
poetry run python src/gui.py
```

This launches a local web server (default: http://localhost:7860) with:

- **Event log selection**: Dropdown to select event logs from the `logs/` directory
- **LLM selection**: Choose one of the supported Ollama models (or type any other model tag pulled on your Ollama server)
- **Thinking**: Toggle reasoning for models that support it
- **Temperature**: Slider to control LLM creativity
- **Max iterations**: Number of improvement cycles to attempt
- **Report display**: Final improvement report shown on completion

The GUI runs the same pipeline as the CLI but with a user-friendly interface.

## LLM Setup (Ollama)

Hypotheses and reports are generated by a model served by Ollama through the official [`ollama`](https://github.com/ollama/ollama-python) Python client. No API keys or cloud accounts are needed.

Supported models:

| Model | Parameters | Max context | Thinking | Pull |
|-------|------------|-------------|----------|------|
| `qwen3.8:latest` (default) | 27.3B | 262k | yes | `ollama pull qwen3.8:latest` |
| `laguna-xs-2.1:latest` | 33.4B | 262k | yes | `ollama pull laguna-xs-2.1:latest` |
| `gemma4:latest` | 8.0B | 128k | yes | `ollama pull gemma4:latest` |
| `qwen2.5-coder:14b` | 14.8B | 32k | no | `ollama pull qwen2.5-coder:14b` |

Any other model available on your Ollama server can be passed with `--model`.

Configuration:

- **Server**: set `OLLAMA_HOST` in `.env` (see `.env.sample`) to use a non-default or remote Ollama server. The pipeline checks the server and the model before starting the (long) SIMOD discovery.
- **Context window**: Ollama silently truncates prompts longer than the context window, so the pipeline sets it explicitly (`--num_ctx`, default 32768, capped at the model maximum). It logs prompt/output token counts for every call and warns when the window is nearly full. Changing `num_ctx` makes Ollama reload the model, and larger windows need more (V)RAM.
- **Thinking**: off by default. With `--think`, reasoning tokens count towards `--max_tokens`, so raise it (e.g. `--max_tokens 16384`) to leave room for the answer. Reasoning traces are stripped from the output.
- **Structured output**: hypothesis generation uses Ollama's JSON mode (`format="json"`) to keep local models from wrapping the hypothesis in prose; the existing parser and fallback still handle malformed answers.

## Architecture

```text
Event Log (XES/CSV)
  -> PM4Py baseline KPIs extraction
  -> SIMOD simulation model discovery
  -> Iteration loop:
       LLM hypothesis generation
       Parallel simulation (Control-flow-first + Resource-first)
       Averaged validation (KPI score > 0.01)
       Utilization veto (reject if overall resource utilization > 90%)
       Scenario update (if the improvement hypothesis is validated)
  -> Improvement report generation
```

## Simulators

The pipeline runs **both simulators in parallel** for every LLM-generated hypothesis, averaging their results for its validation. In this way, control-flow-first captures queue-based capacity effects and resource-first simulation captures behavioral patterns, and averaging provides a more robust validation that neither simulator alone can achieve.

| Simulator | What it Models | Reliable KPIs | Limitations |
|-----------|----------------|---------------|-------------|
| **Control-flow-first (Prosimos)** | BPMN, resource pools, calendars, queuing | cycle_time, waiting_time, throughput | No agent routing/handover |
| **Resource-first (AgentSimulator)** | Agent behaviors, handover sequences | cycle_time, resource utilization | No queue model (waiting_time = 0) |

## Validation

Each simulator computes a score, then scores are averaged:

```
score = delta_throughput - delta_cycle_time
averaged_score = (control-flow-first_score + resource-first_score) / 2
```

**Pass condition:** `averaged_score > 0.01` (1% improvement threshold)

Improvements are **rejected** if average resource utilization exceeds 90%, regardless of score to prevent overloading resources.

## Hypothesis Priority

The pipeline focuses on actionable interventions on resources:

1. *shift responsibility* between resources with the same role (preferred when workload imbalance exists);
2. *resource allocation*, hiring new resources with a specific profile; and
3. *calendar updates* for specific resources.
